## Architecture finding

The repository previously relied on Laravel's default `VerifyEmail` and `ResetPassword` notifications and had no application mail views or mailables. The implementation keeps those notification classes and their framework URL/token behavior, and registers only `toMailUsing` presentation callbacks in `AppServiceProvider`.

The new `EmailDesignSystem` factory returns a `MailMessage` with shared HTML and plain-text views. The Blade system is split into layout, header, footer, button, panel, and transactional templates so future notifications can reuse the same presentation without duplicating email HTML.

The current email-change flow is manual staff approval and does not dispatch an email. No new email was added for that flow because adding delivery would change existing business behavior.

## Security and compatibility review

- Verification notification remains Laravel's `VerifyEmail` class; its signed URL is still generated by the framework callback.
- Password reset notification remains Laravel's `ResetPassword` class; the token is not changed, and the reset route remains `password.reset`.
- `MailMessage` action properties are populated, preserving existing contracts and tests.
- Dynamic recipient text and URLs are escaped by Blade output encoding.
- No token, password, secret, PII record, schema, route, or security policy was logged or persisted by this work.
- HTML uses table-based layout, inline styles, a plain-text alternative, absolute brand asset URL generation, mobile media rules, and a table-backed CTA for Gmail/Outlook compatibility.
- Remote logo loading depends on the configured public `APP_URL`/brand asset being reachable in the receiving mail client; this needs manual environment verification.
