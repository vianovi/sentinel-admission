# Candidate Status Flow and Feature Gates

## Overview

Candidate lifecycle is centralized under `app/Services/CandidateStatus`.

The admission status column stays focused on admission progress:

```txt
draft -> submitted -> verified -> accepted / rejected
```

Email verification is separate account-security state stored in `users.email_verified_at`.

## Status Meaning

| Status | Meaning |
| --- | --- |
| `draft` | Required core registration data is incomplete. |
| `submitted` | Required candidate, guardian, and health data is complete. |
| `verified` | Required documents are verified, BPJS/JKN health document exists, and required payment is paid. |
| `accepted` | Final manual decision. Automatic sync never overwrites it. |
| `rejected` | Final manual decision. Automatic sync never overwrites it. |

## Central Services

| Service | Responsibility |
| --- | --- |
| `CandidateCompletionEvaluator` | Evaluates candidate core data, guardian data, conditional guardian data, and health data. |
| `CandidateVerificationEvaluator` | Evaluates required verified documents, transfer letter when applicable, BPJS/JKN document, and paid payment. |
| `CandidateStatusService` | Synchronizes lifecycle status after events. Uses `updateQuietly()` for automatic status writes. |
| `CandidateGateService` | Provides backend feature gates and human-readable locked reasons for core data, documents, payment, and exam. |

`CandidateVerificationChecklist` remains as a compatibility wrapper and delegates to the new services.

## Core Completion Rules

Candidate fields:

- `phone_number`
- `religion`
- `family_card_number`
- `postal_code`
- `school_npsn`
- `program_choice`

Guardian fields:

- `mother_name`
- `income_type`
- `father_status`
- `mother_status`
- `no_kk`
- `marital_status`

Conditional guardian fields apply when `marital_status !== nikah_tercatat`:

- `guardian_name`
- `guardian_relation`
- `guardian_date_of_birth`
- `guardian_education`
- `guardian_phone`
- `guardian_province`
- `guardian_city`
- `guardian_district`
- `guardian_village`
- `guardian_address`
- `guardian_postal_code`

Health fields follow the stricter backend/model/dashboard rule:

- physical fields: blood type, rhesus, height, weight, general health condition, both eye types
- health history fields: major illnesses, last illness, food allergy, medicine allergy, allergy condition, physical disabilities

## Verification Rules

Required verified documents:

- `photo_formal`
- `birth_certificate`
- `family_card`
- `parent_id_card`
- `graduation_certificate`
- `report_card`
- `parent_statement`
- `transfer_letter` only when `candidates.is_transfer = true`

Additional verification requirements:

- `health_records.bpjs_card_path` must exist.
- At least one payment must have `payments.status = paid`.

## Gate Rules

Documents:

- allowed only if candidate is at least `submitted`
- allowed only if account email is verified

Payment:

- allowed only if candidate is at least `submitted`
- allowed only if account email is verified

Exam:

- allowed only if candidate is at least `verified`
- allowed only if account email is verified

Locked reasons are generated by `CandidateGateService`, and controllers use the same service that frontend props receive.

## Sync Triggers

Lifecycle sync is called after:

- candidate data changes
- guardian data changes
- health data or BPJS document changes
- document upload/delete/review
- payment create/upload/cancel/manual verification/manual rejection
- gateway status polling
- Midtrans webhook paid/final events
- candidate dashboard/document/payment/exam gate checks

## Final Status Protection

`accepted` and `rejected` are final manual decisions. Automatic lifecycle sync returns a protected result and does not modify those statuses.
